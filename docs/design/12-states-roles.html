12States & roles

Every empty state is the published anatomy — a drawing from the trade, a heading, one or two sentences, the secondary action before the primary — because this is where a prospect first meets the product: every screen is empty on day one. The other answers — loading, not allowed, unreachable, not here, gone wrong, signed out — are sentences in the customer’s words with a next step; no code or id reaches the screen. A whole-page answer is an empty state with one primary action, as published; a refusal inside a screen is a section message.

Design note

Three things at once, and they are three different jobs. The banner says the submit failed and that nothing was saved — it is what a screen reader reaches first and what stops somebody assuming a half-written record now exists. The field messages say where, so nobody scrolls a long form hunting for the red one; each control carries aria-invalid and points at its own message with aria-describedby. And the message says what to type — “pick 14 September or later” rather than “invalid date”. The third field is untouched and stays untouched: marking valid fields green is noise, and it makes the two that need work harder to find.

Design note

The difference matters. Empty because it is new is an invitation — the illustration, one sentence, one action that creates the first record. Empty because a filter excluded everything is a dead end the person built themselves, so it names the filters that did it, says which one is the culprit, and offers to undo them. Offering “Add a rate” here would be the wrong button: the items exist; the filters hid them.

Design note

Which wait gets which. A page or a list loading for the first time is a skeleton of its own shape, so nothing moves when the rows arrive. A short wait inside something already on screen — a record opening beside its list, an approval being saved — is a spinner in that place; the button keeps its size and the person keeps their place. A long job whose size is known — an export of 4,000 orders, an upload — is a progress bar that says how far it has got, and the person can keep working. An unknown amount is never a progress bar.

The same three screens as three people — the three the seed has: the admin, procurement and finance. The navigation is identical in all of them — that is not an oversight, it is the shipped rule: a tab hidden in the browser is not an access control, because the URL still resolves. What changes is what the server sends and what it refuses, and a refusal is drawn as itself. The seed has no site engineer, quantity surveyor, designer or salesperson; where a screen needs one, procurement or the admin plays it.

You cannot record a spend here

Recording is the site’s entry — the person who spent the cash makes it, with the receipt. You reconcile and export. Separation of duties is the point, so the button is absent rather than disabled: a disabled button is a promise that pressing it would work.

Design note

Three shapes of “no”, and they are different things. Refused is a thing you may not do, said out loud with the reason and a request id — the person who raised the order, on its approve button. Absent is a control that is not part of your job at all, so it is not drawn — the accountant has no “record a spend”, because a disabled button is a promise that pressing it would work. Never sent is data the server does not return to your role — procurement’s Today has no margin card, and no gap where one would be. Drawing all three as an empty table, which is what the legacy does, is how people learn to distrust a screen.

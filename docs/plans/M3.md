## The gate, stated plainly

ADR-0014 forbids shipping a filed figure computed under a rule no chartered
accountant has seen. That has **not** been relaxed. What this milestone does is
separate two things that were tangled together:

- **the pipeline** — where rounding happens, how a rate is selected for a date,
  how a voucher is built, how acceptance is judged. Correct independently of any
  number, and tested.
- **the numbers** — every rate, threshold, classification and effective date.
  All open, all `provisional`, none present in this repository.

The pipeline being right is a prerequisite for the numbers being right. It is
not a substitute, and no output of this milestone may reach a return, a challan
or a customer's books until `CA-01` … `CA-09` come back.

**Every fixture rate in the tests is deliberately absurd** — 10% and 20% flat,
effective from 1999; thresholds of ₹1,000 and ₹5,000. A plausible-looking
placeholder is precisely the thing that gets mistaken for a verified figure and
promoted by accident.

## Built

### `services/procurement` — a replacement, not a port

One commit, not two, because there is no correct prior behaviour to preserve.
Each decision answers a defect ADR-0014 or TOPOLOGY already classifies as
blocking:

| Legacy | Replacement |
|---|---|
| `write.js:55` trusts a client-supplied `gst_amount`; `:157` trusts the line total itself | Totals are computed from lines. There is no parameter a caller could use to assert one |
| `po_no` is a **mutable primary key**, cascaded across five tables by loose UPDATEs with no transaction | An immutable surrogate id; the number is a display attribute, free to change without moving anything |
| `financiallyChanged` compares money with `> 0.5` | Exact. The tolerance existed only because money was `REAL` |
| Optimistic locking applies only when the client sends `expectedVersion` | Required. The client does not choose whether concurrency control applies to its own write |
| Workflow state is `stage.includes('reject')` | An explicit enum with a declared transition table |

The *arithmetic* — quantity × unit rate, a GST percentage — is faithful, and
goes through `packages/money` with a named boundary. `Quantity` is a branded
scaled integer, because BOQ lines are 12.375 sqm and a float there re-enters
money through the back door.

### `services/finance`

- **Effective-dated rate lookup.** The mechanism, seeded with nothing. Throws
  when no rate is in force rather than defaulting to zero — `Number(v) || 0` is
  how a return gets filed with no tax on it. Rejects overlapping rows rather
  than silently picking one.
- **GST split**, Sec 170, per invoice per tax head. Property-tested:
  `cgst === sgst` always, and `|igst − (cgst + sgst)| ≤ ₹1` with the bound shown
  to be reachable.
- **TDS** — base composition and threshold crossing, with the rate, the
  threshold, the GST-inclusion choice and the rounding boundary **all
  parameters**. Legacy tracks no thresholds at all, so this is new.
- **Tally XML**, written from scratch per ADR-0014's addendum. Full envelope,
  `ALLLEDGERENTRIES.LIST` double entry that must balance to zero,
  `SVCURRENTCOMPANY`, a stable `REMOTEID`, normalised dates — and **escaping**,
  with `M/s A&B Interiors` as a test.
- **`tallyAccepted`** — HTTP 200 is not success. `CREATED=0` with `ERRORS=0` is
  a silent no-op and is treated as failure. This is the defect that made every
  historical "Synced" row meaningless.

### Payment requests

Finance owns the **lifecycle state**; it does not own **entitlement**. Which
roles must sign, in what order, above what amount is configuration, it is
generic across purchase orders, payment requests, change orders and imprest, and
it belongs to `services/workflow` in M4. Nothing in the aggregate knows a role
name or a threshold — `approve()` takes the approver as an input and validates
only that the transition is legal.

`amountRequested` and `amountApproved` are kept separate rather than collapsed
into one mutable field, because "approved for less than requested" is a common
outcome and collapsing them makes it inexpressible and unauditable. That models
the legacy `approved_amount ?? amount_requested` precedence, which ADR-0011
names as a rule existing only in the legacy source — expressed once, in
`effectiveAmount()`, instead of repeated at four call sites as it is today.

**Which accounting view this is.** The legacy contains two that can disagree:
`calculateProjectOutflowSnapshots` asserts a "single-leg approach: ALL payments
flow through system_payments" while `summarizeRequests` in the same file buckets
by substring-matching `stage`. This model is the **request-ledger** view — one
explicit state per request, outflow is the sum over remitted requests. The
reconciliation against legacy figures is M2.5 and is expected to differ; that
difference is the archaeology ADR-0014 requires be agreed with the customer
before go-live.

### The voucher queue

`claim` is **one statement**, not a select followed by an update:
`... FOR UPDATE SKIP LOCKED` inside a CTE feeding an `UPDATE ... RETURNING`.
This is the one place in M3 where a race corrupts a book of account rather than
returning a stale row — two connectors polling simultaneously would both win a
select-then-update and both post to the customer's Tally. Proven by a test that
issues two concurrent claims for twenty vouchers and asserts every id appears
exactly once.

A `posted` report is terminal and is accepted regardless of who holds the lease:
refusing a late report from an expired instance would leave a voucher
re-offerable when it is already in the customer's books. A late `failed` cannot
resurrect a posted voucher.

### `/connector/v1`

Implemented against the contract **as frozen**. The staging table carries lease
columns, a dead-letter state and a per-tenant-unique `remote_id`.

Two deliberate non-gates, each with a comment saying why:

- `/health` is never version-gated — it is how a stale connector discovers what
  to install.
- the result endpoint is never version-gated — a result is a fact about Tally,
  not a request for service, and refusing it would strand a posted voucher and
  cause a re-offer.

Isolation on the staging table is a **book-integrity** control, not a privacy
one: the connector forwards opaque XML, so a row visible to the wrong tenant is
a write into the wrong set of books. The isolation suite asserts it directly.

## Evidence

```
pnpm typecheck         EXIT=0
pnpm lint              EXIT=0
pnpm build             EXIT=0
pnpm test              EXIT=0
pnpm test:isolation    EXIT=0   (2 packages, 30 tests)
```

**M3's stated done-when — PO → approval → payment request → TDS → staged Tally
voucher — runs end to end against a real database**, with the connector
authenticating by bearer key, pulling the voucher, and reporting the result.
Money is conserved across the whole path: what the vendor receives plus what is
withheld equals exactly what was approved.

Every rate in that test is synthetic. What it proves is that the pipeline
carries a figure without losing or inventing money, not that the figure is
right.

The isolation suite grew to cover the staging tables: one tenant cannot see or
lease another's staged voucher, and `remote_id` is unique per tenant rather than
globally — a global constraint would let one tenant learn, from a violation
message, that another had staged a document.

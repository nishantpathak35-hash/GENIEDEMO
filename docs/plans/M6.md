# M6 — The portals, the back office, and self-service onboarding

**Status:** provisioning and the portals built · impersonation not built · **Date:** 2026-09-05 · **Milestone:** M6 of M1–M6

M6's done-when, from KICKOFF: *onboarding a tenant is self-service, with no SQL
run by hand.*

That sentence is the whole milestone. Everything else here exists to make it
true, and the reason it is not a footnote is in TOPOLOGY: **`admin` is net new
and non-negotiable — without it, onboarding a company means running SQL by
hand.** Today it means exactly that. `services/tenancy/scripts/seed.mjs` is how
a tenant comes into existence, and it is a development script that connects as
the migration role.

### The order this was built in, and why

**Policy first, screens second.** M6 states it: *"Not done when: a screen exists.
A portal that renders is not a trust boundary; the policy is."* The scoping
control and its fourteen tests landed before a single portal screen, because a
vendor-facing order list built against unscoped endpoints is a screen that shows
a vendor its tenant's whole order book.

### Money views left out of the portals

Each is CA-gated, and each is absent rather than stubbed — a placeholder that
computes a figure is the outcome worse than not finishing.

| Portal | Left out | Waiting on |
|---|---|---|
| `vendor-portal` | TDS visibility on a bill or an order | **CA-05..CA-08** |
| `vendor-portal` | The retention ledger, and any release | **CA-01..CA-08**, and RET-02 (the legacy release writes no payment record) |
| `client-portal` | The client billing ledger — RA bills raised, money received, balance due | **CA-01..CA-08** |
| `client-portal` | Any billing percentage | Derived from money, so the same gate. The legacy caps it at 100 with `Math.min`, so an over-billed project reads as exactly complete |

What a vendor *can* do is see the orders issued to them, accept or reject one,
and submit a running-account bill. **A claim is not a payable**: the amount is
stored exactly as submitted, nothing deducts from it, nothing nets it, and there
is no approved-amount column for a later step to fill in.

## The three trust boundaries, restated

Four apps exist because there are four **trust boundaries**, not four feature
sets (TOPOLOGY). In the legacy system a vendor authenticates into the same
deployable that serves director-level P&L. That is the single most common
finding in a B2B security review, and separating the deployables is what makes
the finding not apply.

| App | Principal kind | May never reach |
|---|---|---|
| `apps/web` | `staff` | — |
| `apps/admin` | `staff`, platform-scoped | a tenant's data without an impersonation record |
| `apps/vendor-portal` | `vendor` | anything not linked to that vendor's own POs |
| `apps/client-portal` | `client` | vendor pricing, internal margin, any other project |

`identity.principals` has carried `kind` with a CHECK constraint over exactly
these values since migration `0003`, so the distinction existed in the schema
before it existed in a screen. What did **not** exist was anything that narrowed
such a principal to its own rows — *"a `vendor` principal today would see
everything its tenant sees"*, which this milestone called its central piece of
work and a policy problem rather than a UI one.

**That is now closed**, and by a policy rather than a screen:

- `identity.principal_links` (`0023`) records what a non-staff principal is
  entitled to, read inside the transaction by `loadPrincipalScope`. A principal
  with **no link is scoped to nothing**, so the failure direction of a missing
  grant is no data rather than all data.
- `/api/v1/portal/*` is the only surface a non-staff principal may reach, and
  the subject it scopes to comes from the link — never from the request. A route
  taking the id from its path would be an access control whose input the caller
  supplies, which is exactly what `VendorPortalView.js:22-27` does.
- Every other `/api/v1` route is behind `requireStaff`, on the sub-app rather
  than on each route, so a service route added later is behind it by
  construction rather than by remembering.

The tests that say so are in `services/host/tests/isolation/tenant-routes.test.ts`
and assert, among other things, that a vendor linked to V cannot read an order
belonging to W **in the same tenant** — where row-level security contributes
nothing, because V, W and the staff who raised both orders share a tenant.

## Migration prefix allocation — ABANDONED 2026-09-06

**This scheme is abandoned. Take the next free number.** Migrations are past
`0081`; the table below stops at `0060+ unallocated` and nobody has claimed a
block since. It is kept as history, not as instruction.

It was abandoned rather than repaired because **the thing it was protecting is
already enforced by code, and better**:

- `scripts/migration-plan.mjs:65-72` throws on a duplicate prefix and **names
  both offenders**, which is the dangerous case and the only one that can
  corrupt an ordering.
- `services/host/tests/migration-order.test.ts` asserts the plan orders by
  numeric prefix across services, is independent of filesystem order, and
  refuses an ambiguous plan rather than picking one.

A pre-allocated block adds nothing to that. It cannot prevent a collision — only
the runner can, and it does — and it introduces a second place to be wrong. It
was wrong twice: `0020`–`0022` were allocated to `siteops` and taken by
`procurement` and `projects` (recorded below), and every prefix from `0060` on
was written without anyone claiming it here.

**The rule, in full: take the next unused number, put the migration in the
service that owns the table, and never edit an applied file.** If two people
race, the runner refuses the plan and names both files, which is a better
outcome than a table nobody read.

Recorded as `TOOLING-DEFECTS.md` defect 9 — closed by abandonment, which is one
of the two acceptable answers. The other was enforcement, and there is nothing
left to enforce.

## Self-service onboarding — what it has to replace

`seed.mjs` does five things by hand, and each is a requirement in disguise:

1. Insert a `tenancy.tenants` row **inside a tenant context**, because the table
   is `FORCE ROW LEVEL SECURITY` and even the owner is subject to its policy.
2. Insert an `identity.principals` row for the first user.
3. Call `identity.register_principal` so the bootstrap lookup can resolve them.
4. Choose a `slug` and an `app_origin` — the latter is where `auth.js:253`'s
   hardcoded demo domain went, and it is per-tenant precisely so that no invite
   URL is ever a constant again.
5. Mint the runtime role's login.

The chicken-and-egg problem is (1) and (3): **creating a tenant is the one
operation that cannot run inside that tenant's context, because the context does
not exist yet.** The connector-key path already solved the same shape — a
SECURITY DEFINER function owned by `app_auth`, granted narrowly, returning ids
and nothing else — and provisioning follows it rather than inventing a second
mechanism. `withoutTenant` in `packages/service-kit` exists for exactly this and
is purpose-limited on purpose.

**Provisioning is the highest-privilege operation in the product.** It creates a
tenant and its first administrator, so it is the one path where a flaw yields
someone else's data rather than merely their own. It gets its own audit record,
its own rate limit, and a platform-scoped principal — never a tenant-scoped one.

## Impersonation

Support cannot debug what it cannot see, and "log in as the customer" without a
record is indistinguishable from an insider reading a customer's books.

- An impersonation session is a **distinct principal kind**, never a swapped
  `tenant_id` on an existing session.
- It writes an `workflow.audit_events` row on start and on end, and every action
  taken inside it carries the impersonator's id **as well as** the impersonated
  principal's.
- It is time-boxed and cannot be renewed silently.
- It is refused for any route that writes money.

The audit table is already append-only by privilege — `app_runtime` holds
`SELECT, INSERT` and no `UPDATE` or `DELETE`, which the isolation suite proves
by failing when a test harness tried to clean up after itself.

## Done when — the evidence

Nothing is marked done without pasted passing output.

1. **A tenant is created through the API, by an authenticated platform
   principal, with no `psql` and no script.** The test creates one, then
   authenticates as its first user and reads back an empty project list —
   proving the tenant exists and is reachable, not merely that a row was
   written.
2. **`seed.mjs` is reduced to calling that API.** If a development script and
   the product do provisioning differently, the one that is exercised daily is
   the one that stays correct, and it is not the product's.
3. **A vendor principal in tenant A, linked to vendor V, cannot read a purchase
   order belonging to vendor W in the same tenant** — through the route, not
   only at the table. Intra-tenant authorisation is a *separate control* from
   tenant isolation (M1/D3), and this is the test that says so.
4. **A client principal cannot reach any vendor pricing field**, asserted on the
   response body, not on the query.
5. **An impersonation session produces exactly two audit rows and cannot write
   money** — the write is refused with `FORBIDDEN` and the refusal is recorded.
6. `pnpm turbo run test:isolation --force` covers every new table, and the
   introspection test (M1/D8) still reports zero tables without a policy and
   zero float columns.
7. All four apps build, and `pnpm turbo run typecheck` covers 17 members.

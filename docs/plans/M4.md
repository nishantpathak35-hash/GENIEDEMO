## The finding that outranks the rest

The legacy approval chain is **not a control**. Three defects compound:

| | |
|---|---|
| **APPR-01** | The advance loop keeps going while the caller holds the next role, and `admin`/`director` are **exempt from the break**. One call from an administrator carries a request from the first stage to the last. |
| **APPR-02** | There is **no server-side self-approval check**. The only creator comparison is client-side, and it gates loading a *summary* rather than the approve action. |
| **APPR-03** | `approval_workflow_stages` declares **nine** fields and the engine evaluates **one**. Configuring "two approvers required" silently yields one. |

A three-stage approval that one person can satisfy alone, on their own request,
with a configured quorum that is ignored, is a control-shaped hole. Separation
of duties is the first thing a SOC 2 auditor tests, and
`ENTERPRISE-READINESS.md` already flags that a solo team cannot fake it.

**The replacement advances exactly one stage per call, always.** No role
bypasses it. Self-approval is refused regardless of role. `minApprovals` is
honoured, by *distinct* people, and the database carries a
`UNIQUE (tenant, entity, stage, approver)` so one person cannot satisfy a
quorum twice even if a future code path bypasses the engine.

An administrator who must push something through now does so at each stage,
leaving one history row per stage with their name on it — visible rather than
invisible.

**PO-13 is no longer "list the roles".** Somebody must decide the real chain:
which roles sign, in what order, how many approvers per stage, and whether any
role may legitimately act at more than one stage.

## Ported, in two commits each

| Module | Commit 1 records | Commit 2 fixes |
|---|---|---|
| CPWD 4-factor rate engine | **Three** implementations giving **three different answers** on identical input — 481 stored, 482 displayed, 481.88 in a test whose own comment says 481.87 | Paise precision throughout; branded inputs; tax removed from the rate |
| DPR manpower | `parseInt` takes a prefix of free text (`'12 workers'` → 12, `'0x10'` → 16); a malformed count becomes NaN or lowers the total; negatives subtract | Whole non-negative counts only, raising rather than guessing; plus a per-trade breakdown the legacy cannot produce |
| Approval chain | APPR-01 above, demonstrated | One stage per call, no bypass |

Legacy values are kept in the tests as **recorded divergence**, so M2.5's
reconciliation can attribute a difference to a specific change rather than to
"the rewrite".

## Replaced, not ported

Where rule 3 or ADR-0014 already classifies the behaviour as broken, there is no
verbatim commit — there is no correct prior behaviour to preserve.

- **BOQ** (`BOQ-01`): `Number(realPayload.amount) || …` lets a client-supplied
  line amount win. Same hole as `write.js:55`.
- **Change orders** (`CO-01…03`): approval bypasses the engine, rewrites the
  contract value **in place** so the originally signed figure is lost, and
  `decision === 'Reject'` treats **everything else** — a typo, an empty string,
  a missing field — as approval. A client portal that approves a contract
  variation by default is not a signature.
- **Document vault** (`VAULT-01…03`): signed contracts sit in a **publicly
  servable directory**; file bytes are base64'd into a `TEXT` column; uploads go
  through Cloudinary *and* `fs.writeFile`.
- **Event stream**: replaces a 2-second poll per connected client.

## Two properties worth stating plainly

**`NOTIFY` is not subject to RLS.** Every listener on a channel receives every
payload regardless of tenant. So the payload carries `tenantId` and `id` and
nothing else, and the subscriber re-reads the row through `withTenant` — the
only policy-checked path. The isolation suite writes a bank account into the row
and asserts it does *not* appear in the notification.

**Object storage is outside Postgres**, so no policy protects it. Keys are
tenant-prefixed, ids are validated against anything that could escape the
prefix, signed URLs are capped at 15 minutes and refused outright for another
tenant's object — once issued, a signed URL is a bearer credential that no later
policy can revoke.

## Completed after the first pass

- **Takeoff** (`TAKE-01…03`): `it.clientRate || Math.round((it.costRate || 100) * 1.25)`
  is three inventions in one line — a 25% markup with no basis, a bare `100`
  standing in for an unknown cost, and `||` swallowing an explicit zero. The
  replacement returns `null` for a missing rate and **names** the unpriced items
  rather than totalling over the priced subset, which is how an under-priced
  quotation goes out. Export is refused while any item is unpriced.
- **WPR aggregation.** What a weekly report must get right is not arithmetic but
  *which days are missing*: a week that silently averages five submitted days as
  though they were six reads as a slow week, and that figure supports a progress
  claim. Missing dates are named, the denominator is stated, and issuing to a
  client is refused while gaps exist.
- **`APPR-05` closed.** The decision, its history row, its audit row and its
  event are **one transaction**. Proven against a real database: when the
  caller's own state change throws, all four roll back together; when the
  decision is refused, nothing is written at all — a history row for a refused
  decision reads, later, as an approval that was reversed.

**The test harness proved the guarantee by failing.** The first version of the
atomicity suite deleted from `approval_history` in a `beforeEach`, and every
test failed with `permission denied` — append-only by privilege applies to the
harness too. Counts are now scoped per entity instead.

## What landed

### `packages/service-kit` completed for M2's scope

| Piece | Note |
|---|---|
| Correlated logging | M1. Money is stringified before serialisation — pino emits a bigint as an *unquoted numeric literal*, so an audit line would lose precision the moment anything parsed it |
| `withTenant` / `withoutTenant` | M1 |
| **Health checks** | Split liveness from readiness. A liveness probe that checks Postgres restarts every container when Postgres blips, converting a recoverable hiccup into an outage |
| **Error handling** | One envelope for every route: a stable code, a safe message, and a `requestId` that genuinely appears in the logs |

The database readiness check does not run `SELECT 1`. It asserts
`current_user = 'app_runtime'` and that the role holds neither `rolsuper` nor
`rolbypassrls` — the condition under which every RLS policy in the system is
silently inert, and one a reachability probe would sail straight past. It is
checked continuously rather than once at boot, because a PgBouncer
`[databases]` entry carrying `user=` can change who the application connects as
long after start-up.

Error mapping never returns the thrown message. The legacy handler returns
`error.message` verbatim outside production — so a stray database error becomes
an API response, table names and all — and inside production invents a
`Math.random()` reference id that is never logged and therefore correlates with
nothing. Postgres `detail` carries the offending value
(`Key (gstin)=(27AAAAA0000A1Z5) already exists`); it is logged and never
returned.

### CI supply chain — ADR-0015's mandatory items

- **`ignore-scripts` is asserted**, so the single mitigation that neutralises
  most historical npm incidents cannot be silently dropped from `.npmrc`.
- **OSV-Scanner**, not `npm audit`, whose signal is too weak to gate on.
- **CycloneDX SBOM** as a build artifact, because enterprise questionnaires now
  request one directly.

Two things worth recording about the SBOM step:

1. `@cyclonedx/cyclonedx-npm` **does not work here.** It shells out to `npm ls`,
   which does not understand a pnpm workspace, and exits 1. Replaced with
   `@cyclonedx/cdxgen`, verified locally: CycloneDX 1.5, 689 components.
2. It runs from a **pinned devDependency** via `pnpm exec`. The fetch-and-run
   invocation is exactly the arbitrary-package-execution surface ADR-0015
   blocks — the workspace guard refused it, correctly, when it was first
   written that way.

> **CI has still never executed.** No repository in this workspace has a git
> remote (PO-01). The workflow is written to be correct on the day one exists;
> until then it is untested, and calling it green would be the same failure
> `TOOLING-DEFECTS.md` exists to prevent.

### `docs/GOLDEN-PATH.md`

The deliverable the done-when actually names. Every step in it is something
that was forgotten or wrong the first time while building `tenancy` and
`identity` by hand — the four registration points, the no-per-package-lint rule,
the composite primary key, the policy pair, the stale-`node_modules` repair.

**No generator.** With seven services total, one would be written once, used six
times, then drift from the path it claims to encode — invisibly, because nobody
re-reads a generator.

### `services/host`

Now composes the kit: `/healthz` (liveness, touches nothing), `/readyz`
(dependencies plus the role assertion), and one `onError` mapping for every
route. The pool lives here and is never exported.

**"CI fails on a deliberate cross-service import"** was satisfied early, during
M1, and is a permanent test rather than a manual check —
`services/host/tests/boundary.test.ts` writes a violating file, asserts lint
fails with the right message, then asserts it passes once removed.

That test exists because the rule spent its entire life not firing: no
TypeScript parser was configured, so any file with a type annotation failed to
parse and its imports were never examined, while TOPOLOGY, the package READMEs
and CI's own comment all described the boundary as enforced.

## Not in M2, and deliberately

The **migration harness** stays minimal — `services/tenancy/scripts/migrate.mjs`
applies files in order, one transaction each, tracked in `migrations.applied`.
A general harness with drizzle-kit integration waits until a second service owns
migrations, so that its shape is driven by two real cases rather than one
imagined one.
